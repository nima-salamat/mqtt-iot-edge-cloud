# IoT Alarm Camera Platform

A multi-user edge-AI security platform built around a Raspberry Pi 4 and a Raspberry Pi Camera. The Pi captures H.264 video with Picamera2, runs YOLOv5n NCNN locally to detect people, and sends alarm evidence and device health to a Django server.

## Capabilities

- Raspberry Pi 4 camera capture through Picamera2 and the Pi's H.264 hardware encoder.
- Local password-protected management page with camera preview, connectivity, edge-AI health, logs and storage settings.
- YOLOv5n NCNN person detection on the Raspberry Pi; inference is separate from video capture.
- Alarm JPEG snapshots with drawn bounding boxes, confidence and normalized box coordinates.
- Persistent offline outboxes for video segments, alarm evidence and device logs.
- Automatic retry with bounded backoff after network or server outages.
- Regular HTTPS heartbeat with camera/model/stream/MQTT state and actual frame-rate metrics.
- Multi-user Django dashboard, Django Admin, per-account device ownership and retention settings.
- One-time QR pairing generated by the signed-in user and scanned by the actual Pi Camera.
- Browser live view through MediaMTX WebRTC/WHEP with short-lived owner-scoped grants.
- Per-user rolling video retention and separate retention for alarm images and device logs.
- Mosquitto MQTT ACLs; per-device HTTPS credentials protect evidence uploads and RTSPS publishing.
- A separate Streamlit operator diagnostics page at /ops.

## Architecture

    User browser
       | HTTPS / Django session
       v
    Django API + User Dashboard + Django Admin
       |                 |                      |
       | PostgreSQL      | MQTT alarm notice    | HTTP/WHEP with short-lived grant
       v                 v                      v
    Database         Mosquitto              MediaMTX
                         ^                      ^
                         | WSS / TLS            | RTSPS / H.264
                         |                      |
    Raspberry Pi 4 ------+----------------------+
      - Picamera2 owns the camera
      - hardware H.264 encoder
      - local MP4 rolling spool
      - YOLOv5n NCNN inference on the Pi
      - alarm snapshots and durable upload queues
      - Flask local management page

Django is the application backend and owns users, device ownership, QR pairing, alarm records, video metadata, logs, retention policies and authorization. The primary user web interface and the administrative interface are both Django. Streamlit is an internal operator-only diagnostics page; it is not the user IoT dashboard.

## Camera, recording and live video

1. Picamera2 configures a 1280x720 main stream and a 640x360 low-resolution stream.
2. The Pi 4 H.264 hardware encoder targets 30 FPS and feeds both outputs from one encoded camera stream.
3. The local output rotates into short MP4 segments (5 seconds by default). Completed segments form the Pi's upload spool.
4. A separate RTSPS output publishes the live H.264 stream to MediaMTX over TLS/TCP on port 8322.
5. MediaMTX exposes browser playback through WebRTC/WHEP. Django first issues a short-lived grant to a signed-in device owner.
6. Completed MP4 segments upload to Django over HTTPS with a SHA-256 checksum.
7. A server retention worker removes expired video files and their database records. The default is a rolling 10-minute window for each account.

Live video and local recording are independent. If the Internet or RTSPS connection drops, the Pi continues recording locally and retries the live connection with exponential backoff. Completed video segments remain in the durable HTTPS outbox and upload after connectivity returns. The system cannot stream frames live while the network is down; the saved segments provide delayed evidence after reconnection.

The 30 FPS value is a target, not a performance guarantee. Actual capture FPS is reported by the camera encoder and shown separately from the AI inference FPS.

## Edge AI and alarms

- YOLOv5n NCNN runs on the Raspberry Pi, not on the VPS.
- The default inference target is 5 FPS, independently adjustable from the 30 FPS video target.
- The detector evaluates the COCO person class only.
- An alarm is confirmed when person detection is present in at least 2 of the last 3 inference frames.
- An alert cooldown prevents one person remaining in view from producing a continuous sequence of duplicate alerts.
- The Pi saves a JPEG containing the detected person bounding box and stores a JSON event in the local alarm outbox.
- The Pi uploads the image and metadata to Django using the device's unique HTTPS bearer token.
- Only after the server confirms that the alarm evidence is stored does the Pi publish a small MQTT notification with QoS 1.
- The Django MQTT listener links the notification to the already-stored HTTPS alarm. MQTT alone cannot create an alarm, upload an image or impersonate another device's evidence.
- If HTTPS or MQTT is unavailable, the Pi preserves the unfinished step and retries it later.

The YOLOv5n NCNN model is downloaded and integrity-checked by the Pi installer. Its .param and .bin files are installed under pi_device/models on the Raspberry Pi and are not stored as large binary files in this Git repository.

## Device heartbeat and liveness

The Pi sends an HTTPS heartbeat every 15 seconds. It reports camera readiness, YOLOv5n NCNN model state, measured video FPS and inference FPS, RTSPS live-stream connectivity, MQTT alarm-channel connectivity, and pending alarm/video queue counts.

The server considers a device offline after 50 seconds without a successful heartbeat. The server cleanup worker checks this and the per-user retention policy every 15 seconds.

## Users, administration and secure QR pairing

There is no public self-registration page. A staff administrator creates user accounts in Django Admin.

1. The administrator creates a normal Django user and does not grant staff/superuser permission.
2. The user signs in to the Django IoT dashboard and selects Add Camera.
3. Django creates a cryptographically random, one-time QR pairing code that expires after two minutes. Only the signed-in account can query its pairing status.
4. On the Pi's local page, the user selects Scan QR with Camera.
5. Picamera2 temporarily scans the QR using the Pi Camera. The device sends the short-lived code and its persistent device ID to Django over HTTPS.
6. Django validates and consumes the pairing code, assigns the device to that user and returns a unique device API token.
7. The Pi stores its credential file locally with restrictive permissions. The server stores only a password hash of the token.
8. The Pi starts sending heartbeats, alarm evidence and recordings, and publishes its live stream using the same per-device credential.

The QR code is not a permanent password. It is one-time and expires after two minutes. The resulting device token is different for every camera. The Django dashboard queries and media endpoints enforce ownership on the server; hiding another user's camera in the browser is not the security boundary.

Django Admin is available at /admin/. Use it to create normal users, assign/reassign devices, inspect alarms and logs, and revoke a device credential. A disabled user or revoked device token can no longer authenticate its camera.

## Raspberry Pi installation

Requirements:
- Raspberry Pi 4 running Raspberry Pi OS (64-bit recommended).
- A supported Raspberry Pi Camera connected and enabled in the camera stack.
- Raspberry Pi OS package repositories enabled.
- Internet access to the server on HTTPS/WSS TCP 443, RTSPS TCP 8322 and WebRTC ICE UDP 8189.
- Sudo access for package installation and the systemd service.

Clone this repository on the Pi and run from its root:

    chmod +x scripts/install_pi.sh
    sudo ./scripts/install_pi.sh

The installer installs the Picamera2/libcamera, PyAV, OpenCV and NumPy system packages, installs the NCNN Python runtime for ARM (with a source-build fallback), downloads the pinned YOLOv5n NCNN model, verifies the upstream file hashes and sizes, loads the real model and performs a synthetic inference smoke test. It then installs and enables the mqtt-iot-pi systemd service.

Edit /etc/mqtt-iot-pi.env before starting the service:
- Set MQTT_PASSWORD to the MQTT_CAMERA_EDGE_PASSWORD configured on the VPS.
- Set a strong LOCAL_WEB_PASSWORD and random FLASK_SECRET_KEY.
- Verify DOMAIN, API_BASE_URL and RTSPS_HOST.
- Keep DEVICE_ID empty to let the agent generate a persistent unique ID on first launch.

Then run:

    sudo systemctl start mqtt-iot-pi
    sudo systemctl status mqtt-iot-pi
    sudo journalctl -u mqtt-iot-pi -f
    hostname -I

Open http://PI_IP_ADDRESS:8080 from a trusted browser on the local network. This page displays the camera preview and local camera controls. Do not expose port 8080 directly to the public Internet.

## Raspberry Pi local storage and AI settings

These settings are stored on the Pi and are independent from the retention policy configured by each web account.

| Setting | Default | Range |
|---|---:|---:|
| Local video retained after successful upload | 10 minutes | 0–1440 minutes |
| Maximum pending video queue age | 72 hours | 1–168 hours |
| Maximum pending video queue size | 8 GB | 1–64 GB |
| Local uploaded alarm snapshots | 7 days | 1–90 days |
| Local uploaded device logs | 7 days | 1–90 days |
| Video target | 30 FPS | 5–30 FPS |
| AI inference target | 5 FPS | 1–10 FPS |
| Person confidence threshold | 0.45 | 0.10–0.95 |
| Alert cooldown | 15 seconds | 1–300 seconds |
| MP4 segment length | 5 seconds | 2–15 seconds |

Unsent recordings are not removed by the normal local rolling-retention timer. They remain queued until upload succeeds, their retry age expires or the configured size cap is reached. When the queue cap is exceeded, the oldest pending video segments are removed first. Alarm evidence has a reserved portion of the configured queue quota. A prolonged outage can still exhaust storage; use a suitable SD card or external SSD and monitor the local page.

Changing the video FPS, bitrate or segment duration requires a service restart. AI FPS, confidence, cooldown and local retention settings are read dynamically.

## VPS deployment (Docker Compose + host Nginx)

The recommended deployment for a VPS that already runs Nginx on the host is Docker Compose behind that Nginx. Nginx remains outside Docker and owns TCP 80/443. The application containers publish only loopback ports for Nginx; MediaMTX publishes RTSPS TCP 8322 and WebRTC ICE UDP 8189 directly.

Requirements:
- Linux VPS with Docker Engine and the Docker Compose plugin.
- Nginx installed and running on the host.
- DNS A record for `server.echonode.website` pointing to the VPS.
- A valid host-managed TLS certificate and matching private key whose SAN covers the configured domain.
- Public firewall access to TCP 80, 443, 8322 and UDP 8189.

### Clone and configure

Run these commands on the VPS (the example assumes a first installation):

    cd /opt
    git clone https://github.com/nima-salamat/mqtt-iot-edge-cloud.git
    cd /opt/mqtt-iot-edge-cloud
    cp .env.example .env
    chmod +x scripts/*.sh
    nano .env

Set unique values for `DJANGO_SECRET_KEY`, `PANEL_PASSWORD`, `MQTT_CAMERA_EDGE_PASSWORD` and `MQTT_SERVER_PASSWORD`. Generate secrets with:

    openssl rand -hex 32
    python3 -c 'import secrets; print(secrets.token_urlsafe(64))'

Keep the configured domain consistent across `DOMAIN`, `DJANGO_ALLOWED_HOSTS`, `CSRF_TRUSTED_ORIGINS` and `RTSPS_HOST`.

### Database mode

The sample `.env.example` selects `DATABASE_MODE=sqlite` so the platform can be tested without setting up PostgreSQL. In this mode:

- SQLite is stored at `/app/data/db.sqlite3` in the persistent `sqlite_data` Docker volume.
- The same volume is mounted into the API, Streamlit panel, MQTT listener and retention worker.
- The SQLite Compose override disables the PostgreSQL service and removes the API's PostgreSQL dependency.

SQLite is intended for a light, single-server evaluation only. It has more limited concurrent-write behavior than PostgreSQL and is not the recommended database for a production installation or multiple application replicas.

For normal production use, set `DATABASE_MODE=postgres` and set a strong, URL-safe `POSTGRES_PASSWORD`. The regular Compose stack starts PostgreSQL, waits for its health check, and uses the PostgreSQL database volume.

Do not delete Docker volumes when stopping the platform. In particular, `docker compose down -v` deletes the database, media and MQTT persistent data.

### Obtain a dedicated TLS certificate with Certbot

This deployment obtains a certificate specifically for `server.echonode.website`; it does not depend on the existing wildcard certificate. Certbot and Nginx run on the VPS host. No Nginx or Certbot container is started.

Before issuing the certificate, create an A record for `server.echonode.website` pointing to the VPS IPv4 address. If an AAAA record exists, it must point to this VPS and IPv6 port 80 must be reachable; otherwise remove the incorrect AAAA record. Allow inbound TCP 80 and 443 in the VPS firewall.

Install Certbot on Ubuntu/Debian:

    sudo apt update
    sudo apt install -y certbot

Create the webroot and install the temporary HTTP-only Nginx site. This lets Certbot perform HTTP-01 validation without stopping or automatically rewriting the existing Nginx configuration:

    sudo mkdir -p /var/www/certbot/.well-known/acme-challenge
    sudo cp deploy/nginx/letsencrypt-bootstrap.conf /etc/nginx/sites-available/mqtt-iot-certbot-bootstrap
    sudo ln -sfn /etc/nginx/sites-available/mqtt-iot-certbot-bootstrap /etc/nginx/sites-enabled/mqtt-iot-certbot-bootstrap
    sudo nginx -t
    sudo systemctl reload nginx

Issue the certificate (replace the email address with an address you control):

    sudo certbot certonly --webroot \\
      -w /var/www/certbot \\
      -d server.echonode.website \\
      --cert-name server.echonode.website \\
      --email YOUR_EMAIL_ADDRESS \\
      --agree-tos --no-eff-email

Certbot stores the certificate and key at:

    /etc/letsencrypt/live/server.echonode.website/fullchain.pem
    /etc/letsencrypt/live/server.echonode.website/privkey.pem

The sample `.env.example` is configured for these paths:

    HOST_CERT_DIR=/etc/letsencrypt
    MEDIA_TLS_CERT=/host-certs/live/server.echonode.website/fullchain.pem
    MEDIA_TLS_KEY=/host-certs/live/server.echonode.website/privkey.pem

The Compose override mounts the entire `/etc/letsencrypt` directory read-only at `/host-certs`. This is intentional: Certbot's `live/` files are symlinks into `archive/`, so mounting only the two files would break those links inside MediaMTX.

The deployment script verifies that the certificate covers `DOMAIN`, is not expired, and matches the private key. Keep `DOMAIN`, `DJANGO_ALLOWED_HOSTS`, `CSRF_TRUSTED_ORIGINS` and `RTSPS_HOST` consistent.

After obtaining the certificate and deploying the Compose stack, replace the temporary bootstrap site with the final reverse-proxy configuration:

    sudo cp deploy/nginx/server.echonode.website.conf /etc/nginx/sites-available/mqtt-iot-edge-cloud
    sudo ln -sfn /etc/nginx/sites-available/mqtt-iot-edge-cloud /etc/nginx/sites-enabled/mqtt-iot-edge-cloud
    sudo nginx -t
    sudo systemctl reload nginx

The final HTTP virtual host intentionally keeps `/.well-known/acme-challenge/` on the webroot, so future HTTP-01 renewals continue to work.

Install the renewal deploy hook so Nginx reloads and MediaMTX restarts only after this certificate is renewed:

    sudo install -D -m 0750 deploy/certbot/restart-media-services.sh /etc/letsencrypt/renewal-hooks/deploy/mqtt-iot-edge-cloud

Test renewal:

    sudo certbot renew --dry-run

The hook skips unrelated certificates. It reloads host Nginx and restarts the MediaMTX Compose service so the RTSPS listener loads the renewed certificate.

### Deploy the Docker Compose stack

After editing `.env`, run:

    ./scripts/deploy_vps.sh

With `PROXY_MODE=compose-nginx`, this validates the selected TLS certificate and key, checks the Compose configuration, creates the Mosquitto credential file, builds the application image, starts the selected database mode and waits for the Django health endpoint.

The Compose files used are:

- `docker-compose.yml`: application services and internal network.
- `docker-compose.nginx.yml`: loopback-only ports for host Nginx and host certificate mount for MediaMTX.
- `docker-compose.sqlite.yml`: used only when `DATABASE_MODE=sqlite`.

### Nginx routes and exposed ports

The final Nginx virtual host is installed in the previous Certbot section. It proxies the Django dashboard/API, Streamlit at `/ops/`, MQTT WebSockets at `/mqtt`, WebRTC/WHEP at `/webrtc/` and HLS at `/streams/` to loopback-only ports.

RTSPS TCP 8322 and WebRTC ICE UDP 8189 are published directly by MediaMTX and do not pass through the HTTP Nginx proxy. Do not install another active virtual host with the same `server_name`.

### Create the first administrator

After the API is healthy:

    docker compose -f docker-compose.yml -f docker-compose.nginx.yml -f docker-compose.sqlite.yml exec api python manage.py createsuperuser

For PostgreSQL mode, omit the final `-f docker-compose.sqlite.yml` argument.

Use Django Admin to create ordinary user accounts. Only staff/superuser accounts can open Django Admin. Normal users sign in to the IoT dashboard and can only access their own cameras, alarms, video and logs.

### Operations

For SQLite mode:

    docker compose -f docker-compose.yml -f docker-compose.nginx.yml -f docker-compose.sqlite.yml ps
    docker compose -f docker-compose.yml -f docker-compose.nginx.yml -f docker-compose.sqlite.yml logs -f api broker mediamtx listener retention

For PostgreSQL mode, omit `-f docker-compose.sqlite.yml`.

The app's backend services are not published on public interfaces. Do not expose the local Pi management port 8080 or the PostgreSQL and raw MQTT ports to the Internet.

## Web interfaces

- User dashboard: https://server.echonode.website/
- Django Admin: https://server.echonode.website/admin/
- Operator diagnostics: https://server.echonode.website/ops/

The Django user dashboard includes registered camera cards, live status, recent alarms, per-device health, live WebRTC view, alarm snapshots and bounding boxes, uploaded MP4 segments, device logs and per-user retention settings.

The Streamlit /ops page is a separate operator diagnostics view for device heartbeats, alarms, uploaded video segments, device logs, Mosquitto and database health. It uses a separate PANEL_USERNAME / PANEL_PASSWORD; it is not the user-facing IoT panel and does not control devices.

## Server retention

The default per-user policy is:

| Server data | Default retention | User adjustable |
|---|---:|---|
| Rolling uploaded video segments | 10 minutes | 1–60 minutes |
| Alarm snapshots and bounding-box evidence | 30 days | 1–365 days |
| Device logs | 30 days | 1–365 days |

The retention worker runs every 15 seconds. When a video segment expires, the stored media file and database row are removed. Alarm rows remain in history after their snapshot file expires. Local Pi retention and server-account retention are independent.

## Network and security model

| Flow | Transport | Purpose |
|---|---|---|
| Pi → Django API | HTTPS TCP 443 | Pairing, heartbeat, alarm image, logs and MP4 segments |
| Pi → Mosquitto | MQTT over WSS TCP 443 at /mqtt | QoS 1 alarm notification only |
| Pi → MediaMTX | RTSPS TCP 8322 | H.264 live stream publishing |
| Browser → Django | HTTPS TCP 443 | Login, dashboard, admin and protected stored media |
| Browser → MediaMTX | HTTPS WHEP + ICE UDP 8189 | Low-latency live camera view |
| Server-internal | MQTT/WSS 9001 and MQTT/TCP 1883 | Alarm listener and operator broker metrics |

The camera-edge MQTT principal can publish alarm notifications only. The django-server identity can subscribe to alarm notifications and broker metrics. The actual alarm image, alert metadata, heartbeat, device logs and archived video require the unique per-device HTTPS token. MediaMTX verifies that device token for RTSPS publishing and a short-lived account-scoped grant for browser playback.

Keep PostgreSQL and the raw MQTT TCP listener private to the Docker/Swarm network. Keep the RTSPS certificate private. Do not expose the Raspberry Pi local port 8080 to the public Internet.

## Operations and checks

Useful Docker Compose commands:

    docker compose logs -f api web broker mediamtx listener retention
    docker compose exec api python manage.py check
    docker compose exec api python manage.py test

Raspberry Pi service:

    sudo systemctl restart mqtt-iot-pi

GitHub Actions runs Python compilation, Django system checks, migration consistency checks and Django tests on pushes and pull requests.

The Pi installer performs model-import and synthetic-inference checks. These checks do not replace a real end-to-end test with the physical camera, QR pairing, public RTSPS port, WebRTC connectivity, MQTT credentials and an actual person-detection scene.
